Gesta · documentation technique

Parcours d'affichage des offres

De la route React au stockage SQLite, cette page décrit le parcours actuel de GET /offers et les points à toucher pour ajouter un filtre par période.

1. Architecture générale

Le projet est un monorepo npm composé d'un frontend React/Vite et d'un backend Express/TypeScript. Le frontend appelle /api/... ; le proxy Vite transmet la requête à l'API et retire le préfixe /api. Le backend suit le découpage route → middleware → contrôleur → service → repository → SQLite. Les mappers convertissent les lignes SQL en objets métier puis en DTO d'API.

L'authentification est transversale : le token est envoyé tel quel dans Authorization, puis authenticate relit l'utilisateur, ses rôles et ses entreprises. authorize contrôle ensuite l'accès à la liste des offres. Le backend détermine donc la visibilité ; le composant React ne reçoit que les offres autorisées.

2. Parcours détaillé, composant React → base de données

1
React

App.tsx route vers OffersPage

App appelle une seule fois useAuth. Après authentification, il rend la route /offres avec user, token et onUnauthorized. La permission d'afficher la route est déjà vérifiée côté frontend.

2
React

OffersPage.tsx déclenche le chargement

La page appelle useOffers(token, onUnauthorized). Elle gère les états chargement, erreur et liste vide, puis transmet le tableau reçu à OfferTable.

3
React

useOffers.ts gère l'état et l'annulation

Le hook lance l'appel dans un useEffect, annule la requête avec AbortController au nettoyage, stocke les offres et redirige vers la connexion en cas de réponse 401.

4
HTTP

frontend/src/services/offers.service.ts appelle l'API

getOffers exécute fetch("/api/offers") avec le token et le signal d'annulation. readJson vérifie la réponse et isOfferList valide la forme de chaque DTO : titre, entreprise, année, période et statut.

5
Backend · Express

app.ts branche les middlewares et le contrôleur

La requête arrive sur /offers. authenticate identifie l'utilisateur, puis authorize(canListOffers) vérifie son droit. Le contrôleur appelle le service et convertit chaque résultat avec toOfferDto avant de répondre en JSON.

6
Backend · métier

offers.service.ts applique la visibilité

visibilityFilter produit un filtre selon le profil : un administrateur voit tout, un étudiant seulement PUBLISHED, et un contact déposant seulement ses propres offres. Le service envoie ce filtre au repository, puis transforme les DBO avec toOffer.

7
Backend · SQL

offers.repository.ts exécute la requête

Le repository joint offers à companies, academic_years et periods. Il applique les filtres reçus, trie par année académique puis par date de création, et renvoie des OfferDbo.

8
SQLite

La base fournit les lignes liées

La migration 001_initial.sql définit offers, academic_years et periods. Une contrainte de clé étrangère garantit que la période et l'année de l'offre correspondent. Le résultat remonte ensuite dans le sens inverse jusqu'à OfferTable, qui affiche chaque ligne.

4. Ajout d'un filtre par période

La recommandation est un filtre côté serveur : l'interface envoie le critère, mais la visibilité par rôle reste appliquée par le backend et le SQL. Cela évite de télécharger des offres qui ne correspondent pas au critère et ne contourne pas l'autorisation.

Fichier concernéÉvolution attendue
frontend/src/pages/OffersPage.tsxAjouter le contrôle (sélecteur P1/P2/OTHER ou deux dates) et conserver le critère dans l'état de la page.
frontend/src/hooks/useOffers.tsAccepter le filtre, l'inclure dans les dépendances de l'effet et relancer la récupération quand il change.
frontend/src/services/offers.service.tsSérialiser le filtre dans la query string, par exemple ?period=P1 ou ?from=2026-09-01&to=2027-01-31.
frontend/src/models/offer.ts et frontend/src/utils/guards.tsÀ modifier seulement si le filtre ou les bornes deviennent des données renvoyées par l'API ; le DTO actuel contient déjà period.
backend/API.mdDocumenter le paramètre, son format, ses limites et les erreurs 400.
backend/src/controllers/offers.controller.tsLire et valider les query parameters avant de les transmettre au service ; rejeter les formats invalides avec HttpError.
backend/src/services/offers.service.tsFusionner le filtre demandé avec le filtre de visibilité, sans permettre au filtre utilisateur d'élargir les droits.
backend/src/repositories/offers.repository.tsAjouter le paramètre optionnel et la condition SQL sur p.code (code de période) ou sur les bornes de p.start_date/p.end_date.
backend/src/repositories/offers.repository.ts et backend/src/models/offer.tsPour un intervalle calendaire, sélectionner aussi les dates de période dans le DBO ou filtrer directement via la jointure ; aucun changement de DTO n'est obligatoire.
backend/tests/offers.test.tsTester le filtrage par période pour administrateur, étudiant et déposant, ainsi que l'absence d'élargissement de visibilité et les paramètres invalides.
frontend/tests/OffersPage.test.tsxTester le contrôle, la query string envoyée et le rendu de la liste après changement de période.
Choix à préciser avant implémentation : dans le modèle actuel, « période » peut désigner le code métier P1/P2/OTHER ou une plage de dates. Pour un simple sélecteur P1/P2, aucun changement de migration n'est requis. Pour de nouvelles bornes ou une nouvelle notion de période, ajouter une migration ordonnée dans backend/src/db/migrations/ plutôt que modifier 001_initial.sql.

5. Flux résumé

App → OffersPage → useOffers → getOffers
  → Vite proxy → authenticate → authorize
  → offers.controller → offers.service (visibilité)
  → offers.repository (jointures + SQL)
  → SQLite: offers ↔ companies ↔ academic_years ↔ periods
  ← OfferDbo → Offer → OfferDto → OfferTable
